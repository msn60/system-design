# چالش‌های اصلی System Design در مقیاس بزرگ 

تقریباً تمام مصاحبه‌های سیستم‌دیزاین یا طراحی سرویس‌های واقعی حول همین چند محور می‌چرخند و عموما این سؤالات مطرح می شوند:

## 1️⃣ چطور scale کنیم؟

وقتی تعداد کاربران زیاد می‌شود، یک سرور دیگر پاسخگو نیست. باید بتوانیم سیستم را طوری طراحی کنیم که با افزایش کاربران، بتوانیم مدیریت scale کردن را به راحتی انجام دهیم. عموما از دو روش vertical scale (افزایش قدرت سرور) و یا horizontal scale (اضافه کردن سرورهای بیشتر) استفاده می‌شود. 

مثلا در روش vertical با مشکلاتی مانند سقف داشتن، گران بودن و Single point of failure مواجه هستیم. 

## 2️⃣ چطور highly available باشیم؟

این مورد با system uptime بیان می‌شود. به عنوان مثال گفته می شود که availability سیستم 99 درصد یا 99.9 یا 99.99 می باشد (که به معنی مدت زمان uptime در طول یک سال می‌باشد). برای این مورد عموما از redundancy (مثل تکنیک های لود بالانس) یا multi- region و ترکیب با آن ها با health check استفاده می‌کنیم.  

## 3️⃣ چطور request از دست ندهیم؟

وقتی ترافیک خیلی زیاد می‌شود، ممکن است سرور نتواند همه درخواست‌ها را هندل کند. یکی از راه حل های این مشکل، استفاده از صف یا message broker هایی مثل kafka یا rabbitmq می‌باشد. 

## 4️⃣ چطور bottleneck I/O را حل کنیم؟

برخی سیستم‌ها CPU-bound نیستند بلکه I/O-bound هستند مثل: 

- file storage
- chat systems
- streaming
- database-heavy systems

به عنوان مثال فید اینستاگرام، یکی از این موارد است که مشکل اصلی در آن DB reads می باشد نه cpu. برای موارد مشابه این مثلا از تکنیک های مثل caching یا read-heavy workloads استفاده کنیم.

## 5️⃣ چطور سیستم را monitor کنیم؟

مساله اصلی در این مورد Observability می‌باشد، این یعنی فهمیدن  اینکه داخل سیستم چه اتفاقی می‌افتد. عموما برای این مورد، سه ستون اصلی داریم که شامل log و metrics و tracing می‌شوند. 

## 6️⃣ چطور سرویس‌ها را decouple کنیم؟

این موضوع درباره Microservice Architecture است. در حالت monolith عموما با مشکلاتی چون deploy و scale سخت و همینطور coupling زیاد طرف هستیم. به عنوان در سیستمی مانند این service A -> service B -> service C مشکل coupling داریم که اگر مثلا سرویس c به مشکل بخورد، همه سیستم down خواهد شد. برای رفع این مشکلات از راه حل های decoupling استفاده می کنیم

## 7️⃣ چطور real-time scale کنیم؟

سیستم های بزرگی همچون whatsApp, slack, Trading system, Uber دارای میلیون ها persistent connections هستند. لذا اینکه چطور آن ها را به صورت  real time مورد scale قرار دهیم، بسیار اهمیت خواهند داشت. 

## 8️⃣ چقدر consistency داده‌ها مهم است؟

در سیستم‌های توزیع‌شده همیشه tradeoff داریم که عموما از تئوری CAP Theorem پیروی می کند. در واقع یک سیستم توزیع شده نمی تواند همزمان دارای consistency, Availability, partition tolerance باشد. در این مورد هم از مواردی چون Strong Consistency (مانند تراکنش  بانکی) یا Eventual Consistency (لایک های اینستاگرام) استفاده می‌کنیم.
