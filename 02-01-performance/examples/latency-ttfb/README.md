# Latency TTFB Example

این مثال برای یادداشت [Latency](../../latency.md) نوشته شده است و نشان می‌دهد که **TTFB** (زمان رسیدن اولین بایت) و **TTLB** (زمان رسیدن آخرین بایت، همان Response Time از دید کلاینت) دو چیز متفاوت‌اند.

## برنامه چه کار می‌کند؟

یک endpoint داریم که 5 آیتم برمی‌گرداند و آماده کردن هر آیتم 100ms طول می‌کشد (شبیه‌سازی یک منبع داده‌ی کند با `time.Sleep`). همین endpoint به دو شکل نوشته شده است:

| Handler | رفتار |
|---|---|
| `/bulk` | همه‌ی آیتم‌ها را آماده می‌کند، یک‌جا JSON می‌سازد و بعد می‌فرستد |
| `/stream` | هر آیتم را (به شکل NDJSON) همین که آماده شد می‌فرستد و Flush می‌کند |

برنامه هر دو را روی یک سرور تستی (`httptest`) بالا می‌آورد، با یک client که با `httptrace` اولین بایت را اندازه می‌گیرد صدا می‌زند و نتیجه را چاپ می‌کند. یک wrapper هم زمان **اولین Write** را در سمت سرور ثبت می‌کند.

## پیش‌نیاز

- Go نسخه‌ی 1.21 یا جدیدتر
- یک فایل `go.mod` در ریشه‌ی ریپو (اگر ندارید: `go mod init system-design` در ریشه‌ی ریپو)
- هیچ کتابخانه‌ی بیرونی لازم نیست؛ فقط کتابخانه‌ی استاندارد

## اجرا

از ریشه‌ی ریپو:

```bash
go run ./02-01-performance/examples/latency-ttfb
```

بررسی کیفیت کد:

```bash
gofmt -l 02-01-performance/examples/latency-ttfb
go vet ./02-01-performance/examples/latency-ttfb
```

## خروجی نمونه

```text
server bulk    first-write= 502ms total= 502ms
client /bulk   TTFB= 503ms TTLB= 503ms
server stream  first-write= 100ms total= 502ms
client /stream TTFB= 100ms TTLB= 502ms
```

عددها در هر اجرا چند میلی‌ثانیه فرق می‌کنند و ترتیب خط‌های `server` و `client` هم ممکن است جابه‌جا شود.

## خروجی را چطور بخوانیم؟

- در `/bulk` اولین Write بعد از آماده شدن **همه‌ی** آیتم‌ها اتفاق می‌افتد (5 × 100ms = 500ms)، پس TTFB و TTLB تقریباً برابرند.
- در `/stream` اولین Write بعد از آماده شدن **اولین** آیتم اتفاق می‌افتد (100ms)، ولی تا آخرین آیتم هنوز 400ms دیگر لازم است. پس TTFB حدود 100ms و TTLB همچنان حدود 500ms است.
- نتیجه: **Response Time تغییر نکرده، ولی کاربر 5 برابر زودتر اولین داده را می‌بیند.**
- اختلاف عددهای `server first-write` و `client TTFB` (حدود 1ms) همان هزینه‌ی شبکه و سربار client است. در این مثال سرور و client روی یک ماشین هستند، پس خیلی کم است.

## آزمایش‌های پیشنهادی

1. زمان `Sleep` را از 100ms به 300ms تغییر بدهید و ببینید TTFB در `/bulk` چقدر می‌شود (انتظار: حدود 1500ms).
2. تعداد آیتم‌ها را از 5 به 10 تغییر بدهید. TTFB در `/stream` باید ثابت بماند و TTFB در `/bulk` دو برابر شود.
3. خط `flusher.Flush()` را حذف کنید. بدون Flush، داده در بافر می‌ماند و TTFB در `/stream` هم بالا می‌رود. این نشان می‌دهد چرا Flush برای streaming لازم است.
4. به‌جای `httptest`، سرور را با `http.ListenAndServe` روی یک پورت بالا بیاورید و با curl بزنید:

```bash
curl -o /dev/null -s -w "ttfb=%{time_starttransfer} total=%{time_total}\n" http://localhost:8080/stream
```

## نکات و محدودیت‌ها

- در `/stream` بعد از ارسال اولین بایت، status code (200) ارسال شده است و اگر در آیتم‌های بعدی خطا رخ دهد، دیگر نمی‌شود آن را عوض کرد.
- این روش فقط وقتی فایده دارد که کلاینت بتواند داده را تکه‌تکه پردازش کند (NDJSON، SSE و مشابه). برای یک JSON آرایه‌ای که کلاینت باید کامل بگیرد، فایده‌ای ندارد.
- اگر بین سرور و کلاینت یک proxy باشد که پاسخ را buffer می‌کند (مثلاً `proxy_buffering` در Nginx)، کلاینت اولین بایت را دیرتر می‌بیند.
- `time.Sleep` فقط یک شبیه‌سازی است؛ در سیستم واقعی این زمان، query دیتابیس یا call به سرویس دیگر است.
